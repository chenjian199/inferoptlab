# TP8 耗时占比与优化方向分析

**整理日期：2026-11-26**  
**分析范围：TP8 / EP 关与开的现有基准测试及 GPU kernel 汇总数据**

> 结论：当前已测负载优先采用 **EP 关**作为优化基线。进一步排查重点是 **AllReduce 单次耗时增加、EP 额外的 copy / index / fill、mHC 两个主核，以及按负载区分的低并发 GEMV 和多并发 MoE GEMM**。开展实现优化前，应先核实 profiling 是否覆盖了完整 prefill，并定位高并发服务端失败。
>
> 本文是对已有文件的重新汇总、对照和分析，未在服务端执行新的实验或修改部署。所有优化收益均需通过后续实验确认。

## 1. 核心结论与行动顺序

| 优先级 | 方向 | 已有证据 | 下一步 |
| --- | --- | --- | --- |
| P0 | 校准采样范围与输入、缓存口径 | execute 注解中的 context 计数很小，完整长上下文 prefill 覆盖尚不明确 | 对齐实际 token、prefix cache、采样窗口、请求 ID 和部署版本的注解代码 |
| P0 | 以 EP 关作为当前基线 | 9 组 benchmark 中，EP 开的 TPOT 均升高、输出吞吐均降低 | 固定环境，交替复测 EP 关/开，确认稳定性 |
| P1 | 排查高并发服务端失败 | 4K/c16、16K/c8、64K/c4 均报告服务端失败 | 找到第一条错误，区分内存、KV 容量、调度或运行时故障 |
| P1 | AllReduce 与 EP 准备操作 | collective 解释了 kernel 累计时间净增的 57.93%～71.15%；三类准备核调用显著增加 | 同时采集通信大小、rank 到达时间、专家负载和调用栈 |
| P2 | mHC 主核优化 | 4K/c1/EP 关下两个主核合计占 15.43% | 针对真实小批量形状优化访存、归约与调度 |
| P2 | other 内碎片算子融合 | other 总占比约 25%～28%；存在重复的 copy、逐元素和归一化候选链 | 先确认模块归属和数据依赖，再选择融合或删除冗余操作 |
| P2 | 按目标区分 GEMV 与 MoE | 低并发 GEMV 权重高，多并发 MoE GEMM 权重升高 | 低延迟目标优先 GEMV；吞吐目标优先 MoE GEMM 与专家负载 |

以上顺序综合考虑证据强度、影响范围和验证成本。P1 中的并发故障定位与 EP 性能定位可以并行进行。

## 2. 数据来源、覆盖范围与统计口径

### 2.1 输入文件

| 来源 | 文件 | 用途 |
| --- | --- | --- |
| [S1] | `TP8.md` | TP8 下 EP 关/开的 TTFT、TPOT、E2E、吞吐，以及失败/跳过场景 |
| [S2] | `families.csv` | 每场景 6 类 kernel family 的累计时间与占比 |

校验未发现缺失 rank 或重复聚合键；调用数能够精确对齐，时间与占比差异处于原表保留小数造成的舍入范围内。原始表未完整记录模型版本、镜像/提交号、硬件型号、物理互联拓扑及采集日期，因此本文不据此推断特定版本的实现能力。[S2]、[S3]、[S4]

benchmark 有 **9 组 EP 对照**，profiling 只有 **5 组 EP 对照**。4K/c2、4K/c4、16K/c2、64K/c2 没有对应的 kernel 明细，不能将其他场景的 kernel 归因直接套用到这些场景。

### 2.2 时间和占比的定义

本文将跨 8 个 rank 累加的 kernel duration 记为 **rank-ms**。这是为避免误读而采用的说明性记法，原始数据时间单位仍为 ms。

```text
场景累计 kernel 时间 = Σ各 rank Σ各 kernel 的 sum_ms
某类占比 = 该类累计 kernel 时间 / 场景累计 kernel 时间
加权单次耗时（μs） = 1000 × Σsum_ms / Σcalls
EP 相对变化 = EP 开 / EP 关 − 1
某类对净增的贡献 = 该类（开 − 关）/ 全部 kernel（开 − 关）
```

需要保持以下口径一致：

- `families.csv` 的占比分母是该场景全部 rank 的累计 kernel 时间。
- 原始 `kernels(1).csv` 的占比分母是对应单个 rank 的累计时间。跨 rank 汇总时必须重新计算，不能直接相加。
- 平均单次耗时按调用数加权，不能把不同调用量的 `avg_us` 简单平均。
- 全部 rank 的累计 kernel 时间不是单请求时延，也不是 TP8 同步执行的墙钟时间；即使再除以 8，也不能据此还原请求时延。
- `union_gpu_ms` 按字段含义表示单个 rank 已记录 kernel 活动区间的并集长度；它不包含区间之间的空闲，也不代表完整采样窗口。缺少原始时间戳和生成脚本，无法独立重建其计算过程。
- `sum − union` 反映已记录区间重复覆盖的部分，不能直接称为通信与计算重叠率、空闲率或 GPU 利用率。

因此，下文的“占比 15%”表示 **累计 kernel duration 的 15%**。只有优化命中端到端关键路径，并且后续测试确认，才可能兑现为用户可见的性能收益。[S2]、[S3]、[S4]

## 3. 先核实：这份 profile 捕获了哪些执行阶段？

### 3.1 注解显示生成阶段占主导

例如 c1 场景包含：

```text
execute_context_1(1)_generation_0(0)       × 1
execute_context_0(0)_generation_1(1)       × 19
execute_context_0(0)_generation_0(0)       × 1
```

上游 vLLM 的相关实现将标签组织为 context 请求数、context token 数、generation 请求数、generation token 数；计算来自本次调度的 `num_scheduled_tokens`。[R1]、[R2]

**只有当前部署的沐曦分支沿用这些上游语义时**，本次注解才能作如下解释。表中数值按一次执行序列统计，8 个 rank 的相同注解不重复累加。[S3]

| 并发 | 非空 execute 注解数 | context token 汇总（条件解释） | generation token 汇总（条件解释） |
| --- | --- | --- | --- |
| c1 | 20 | 1 | 19 |
| c4 | 21 | 4 | 76 |
| c8 | 21 | 8 | 152 |

这里的 context token 计数不能等同于原始 prompt 长度。它可能受采样窗口、已处理的 prefill、prefix cache 或分块执行等影响。现有聚合数据无法区分这些原因，也不能证明 64K 输入从未被处理。

**当前最稳妥的判断是：采样明显以生成阶段为主；完整长上下文 prefill 是否被覆盖仍需确认。** 不宜把 4K 与 64K 场景的 kernel 总量接近，解释成长上下文 prefill 本身很便宜。

### 3.2 建议补齐的证据

先对照 4K/c1 与 64K/c1，保存同一请求的：

1. 实际 tokenization 后的输入 token 数、实际输出 token 数。
2. 已缓存与未缓存的输入 token 数，prefix cache 开关及命中信息。
3. profiler 开始/结束时刻、warmup 与 active 窗口、execute 注解。
4. benchmark 请求 ID 与服务端日志中的请求 ID。
5. 当前镜像、提交号及 `annotate_profile` / `compute_iteration_details` 的实际代码。

冷启动/无缓存 prefill 和缓存命中后的执行应分别报告。**vLLM 的 prefix/KV cache 与 AIPerf 的数据集缓存是不同层面的缓存**：关闭数据集缓存复用，并不能据此认定服务端没有 prefix cache 命中。

| 16K / c1 | 18.44 → 23.04 | +24.95% | 51.04 → 41.42 | -18.85% | 0.39 → 0.48 |
| 16K / c2 | 20.02 → 25.11 | +25.42% | 91.37 → 73.85 | -19.17% | 0.43 → 0.54 |
| 16K / c4 | 21.27 → 26.29 | +23.60% | 167.90 → 137.64 | -18.02% | 0.47 → 0.58 |
| 64K / c1 | 17.23 → 22.20 | +28.85% | 47.08 → 39.16 | -16.82% | 0.42 → 0.50 |

9 组对照给出一致方向：

- 平均 TPOT 增加 **21.45%～28.85%**。
- 输出吞吐下降 **16.82%～20.44%**。
- 平均 E2E 增加约 **19.05%～26.32%**；E2E 原始均值只保留两位小数，相对变化相应受舍入影响。
- TTFT 在 8 组中变差。例外是 64K/c1，从 89.05 ms 降到 80.60 ms，但同场景 E2E 仍从 0.42 s 增到 0.50 s。

建议将 **EP 关作为当前负载的基线配置**。这一结论适用于这些已测场景，不能外推为所有 batch、专家分布、互联配置或模型规模下 EP 都无益。

### 4.1 现有 benchmark 的证据边界

原表每场景重复次数为 1，请求数是并发的 4 倍。c1 只有 4 个请求，其 P95 不能支撑稳定的尾延迟结论。8 个 rank 属于同一次协同执行，不是 8 次独立实验。[S1]、[S3]

20-token 输出下，表内 E2E 大体符合 `TTFT + 19 × TPOT`，但这只是对指标的交叉检查。TTFT 还包含排队、调度等环节，不能直接当作纯 prefill GPU 时间。输出 token/s 与请求 req/s 在固定输出长度下也相互关联，不能视为两项独立证据。

下一步应在稳定环境下交替运行 EP 关/开，至少取得多个独立测量窗口，并扩大有效请求量后再评估 P95。先保持当前 20-token 条件做可比复测，再按真实业务增加更长输出的测试。

## 5. kernel 耗时占比：总体优化机会在哪里？

下表占比统一按该场景 **全部 8 个 rank 的累计 kernel duration** 计算。分类继承原始 family，百分比四舍五入后可能不恰好合计 100%。[S2]、[S4]

| 场景 | other | other GEMM | mHC | MoE | collective | attention / linear attention |
| --- | --- | --- | --- | --- | --- | --- |
| 4K / c1 / EP 关 | 26.87% | 22.40% | 15.76% | 14.83% | 13.75% | 6.39% |
| 4K / c8 / EP 关 | 25.66% | 19.48% | 13.79% | 19.91% | 12.58% | 8.59% |
| 16K / c1 / EP 关 | 27.20% | 22.24% | 15.65% | 14.71% | 13.87% | 6.34% |
| 16K / c4 / EP 关 | 26.42% | 20.50% | 13.47% | 19.93% | 13.00% | 6.68% |
| 64K / c1 / EP 关 | 28.20% | 22.19% | 15.61% | 14.69% | 12.97% | 6.33% |
| 4K / c1 / EP 开 | 27.03% | 20.11% | 14.82% | 14.23% | 18.03% | 5.77% |
| 4K / c8 / EP 开 | 25.17% | 17.25% | 12.47% | 18.47% | 19.05% | 7.59% |
| 16K / c1 / EP 开 | 27.05% | 19.78% | 14.58% | 14.00% | 18.91% | 5.68% |
| 16K / c4 / EP 开 | 25.92% | 18.14% | 12.34% | 18.21% | 19.49% | 5.90% |
| 64K / c1 / EP 开 | 27.95% | 19.72% | 14.54% | 14.00% | 18.13% | 5.66% |

可以据此确定以下关注点：

1. **other 是最大的一组未充分解释的开销**，约占 25%～28%。应继续拆解到 copy、cast、逐元素、量化、索引、填充等可定位的操作。
2. **other GEMM 与 mHC 是 EP 关基线中的主要优化对象**。低并发时它们分别约占 22% 和 15%～16%。
3. **EP 开后 collective 权重明显上升**，从约 12.6%～13.9% 增至约 18.0%～19.5%。
4. **多并发时 MoE 权重提高**，EP 关的 4K/c8、16K/c4 接近 20%。
5. 原表中的 `attention/linear attention` 只是当前分类收集到的核，不是完整 attention 模块的耗时。

占比变化还受分母影响。例如 EP 开后 mHC 占比下降，但其绝对累计时间仍然上升。因此，应同时观察绝对时间、调用数和占比。

## 6. EP 变慢的主要来源：collective 增时与准备操作增加

### 6.1 五组 profile 的总体差分

以下时间单位均为 rank-ms。[S2]、[S4]

| 场景 | EP 关总和 | EP 开总和 | 净增 | 增幅 | collective 增量 | collective / 总净增 |
| --- | --- | --- | --- | --- | --- | --- |
| 4K / c1 | 2545.627 | 2818.923 | 273.296 | +10.74% | 158.314 | 57.93% |
| 4K / c8 | 3443.138 | 3870.938 | 427.801 | +12.42% | 304.376 | 71.15% |
| 16K / c1 | 2564.229 | 2864.915 | 300.685 | +11.73% | 186.148 | 61.91% |
| 16K / c4 | 3209.784 | 3619.179 | 409.396 | +12.75% | 288.216 | 70.40% |
| 64K / c1 | 2570.064 | 2874.014 | 303.950 | +11.83% | 187.659 | 61.74% |

EP 开后，累计 kernel 时间增加 **10.74%～12.75%**。其中 collective 对总净增的贡献达到 **57.93%～71.15%**，other 为 **21.17%～28.56%**，MoE 为 **4.74%～8.70%**。

完整 family 时间差如下，正值表示 EP 开增加，负值表示减少，单位 rank-ms：

| 场景 | collective | other | MoE | mHC | other GEMM | attention / linear attention |
| --- | --- | --- | --- | --- | --- | --- |
| 4K / c1 | +158.314 | +78.065 | +23.789 | +16.477 | -3.467 | +0.117 |
| 4K / c8 | +304.376 | +90.580 | +29.562 | +7.783 | -2.869 | -1.631 |
| 16K / c1 | +186.148 | +77.531 | +23.781 | +16.554 | -3.494 | +0.166 |
| 16K / c4 | +288.216 | +90.189 | +19.399 | +14.146 | -1.750 | -0.804 |
| 64K / c1 | +187.659 | +78.350 | +24.803 | +16.541 | -3.561 | +0.159 |

这里的“贡献”仅用于分解累计 kernel 时间的净变化，不能写成“collective 导致了端到端性能损失的 58%～71%”。profiling 与 benchmark 的采样窗口、请求覆盖和运行条件没有完整对应，也不能把 kernel 增幅约 11% 与 TPOT 增幅约 25% 的差额直接归因于 CPU。

### 6.2 AllReduce：调用次数相同，单次耗时明显增加

对下面这个具体核，5 组 EP 对照中的调用数均未变化：[S4]

```text
mcclKernel_AllReduce_HFC8_LL_Sum_mccl_bfloat16(fcinfo)
```

| 场景 | 调用数：关 / 开 | 关：加权平均 μs | 开：加权平均 μs | 单次耗时变化 |
| --- | --- | --- | --- | --- |
| 4K / c1 | 14,560 / 14,560 | 23.838 | 34.706 | +45.59% |
| 4K / c8 | 15,288 / 15,288 | 27.654 | 47.574 | +72.03% |
| 16K / c1 | 14,560 / 14,560 | 24.215 | 36.995 | +52.78% |
| 16K / c4 | 15,288 / 15,288 | 26.779 | 45.629 | +70.39% |
| 64K / c1 | 14,560 / 14,560 | 22.690 | 35.573 | +56.78% |

**可以确认：这个 AllReduce 核在 EP 开时，观测到的加权单次 GPU duration 增加了 45.59%～72.03%。** 这个结论不能扩展为“所有 collective 的调用数都不变”。

目前不能仅凭这些数字判定互联带宽不足。需要区分：

| 可能机制 | 应补充的证据 | 对应方向 |
| --- | --- | --- |
| 消息大小或通信形态变化 | 每次 collective 的字节数、dtype、通信组、算法选择 | 结合消息大小评估算法与传输效率 |
| rank 到达 collective 的时刻不同 | 同一步各 rank 的 kernel 起止时间、前序计算链 | 优化造成迟到的计算、准备操作或调度 |
| 专家负载不均 | 每 rank/专家的 token 数、GEMM 形状及耗时 | 检查专家映射与路由分布 |
| 拓扑或资源竞争 | 逻辑 rank 到物理卡映射、互联路径、并发通信 | 结合实际拓扑验证配置 |

特别是，某 rank 的 collective 持续时间最长，可能是它更早进入等待；不能直接把它认定为拖慢其他 rank 的来源。应先关联前序计算完成时刻与整个通信组的时间线。

### 6.3 EP 额外增加的 copy / index / fill

EP 开后，每个 rank 的 kernel 总调用数增加：

| 场景 | EP 关每 rank 调用数 | EP 开每 rank 调用数 | 每 rank 净增 |
| --- | --- | --- | --- |
| c1 的三个输入长度 | 42,171 | 44,691 | 2,520 |
| 4K/c8 | 46,723 | 49,369 | 2,646 |
| 16K/c4 | 46,715 | 49,361 | 2,646 |

按 20 或 21 个非空 execute 注解归一化，恰好是平均每个 execute 多 126 次调用；三类核分别对应平均多 42 次。这是聚合数量的归一化结果，尚未用逐步时间线证明每一步都有完全相同的新增序列。[S3]、[S4]

以 4K/c1 为例，以下调用数均为 8 个 rank 合计：

| 核名称特征 | 调用数：关 → 开 | 累计时间：关 → 开（rank-ms） | 累计时间增量（rank-ms） |
| --- | --- | --- | --- |
| direct copy / cast | 160 → 6,880 | 1.046 → 39.423 | +38.378 |
| index，OpaqueType<4> | 160 → 6,880 | 0.467 → 23.670 | +23.203 |
| BFloat16 FillFunctor | 1,760 → 8,480 | 3.387 → 17.071 | +13.684 |

建议优先沿这三类核的调用栈定位实际准备路径，确认是否存在：

- 每轮重复的索引生成、类型转换或布局变换。
- 可以复用而反复构建的工作缓冲区。
- 可与邻接计算合并的 copy 和 index。
- 后续完整覆盖、因而可能不再需要的初始化 fill。

删除 fill 前必须确认所有元素的读写覆盖和跨步复用语义；只凭核名不能认定其冗余。准备操作属于哪个模块、是否相邻、能否融合，都需要调用栈和数据依赖佐证。

另外，某些量化核由一个模板版本切换到另一个版本时，会呈现“一项大增、一项大减”。已有数据中存在量化模板替换而合计时间略降的情况。MoE GEMM 也存在模板切换，应聚合比较功能等价的核，避免把新名称的全部时间误记为新增开销。

## 7. mHC：基线中较明确、较集中的优化对象

4K/c1 下，mHC 的主要时间集中于以下两个核。表内调用数为 8 个 rank 合计。[S4]

| 核 | EP 关 rank-ms | EP 关占比 | EP 关调用数 | EP 关平均 μs | EP 开 rank-ms |
| --- | --- | --- | --- | --- | --- |
| `mhc_pre_big_fuse_with_norm_tilelang_kernel` | 208.213 | 8.18% | 14,400 | 14.459 | 209.401 |
| `mhc_fused_tilelang_kernel` | 184.461 | 7.25% | 14,240 | 12.954 | 199.669 |
| 两核合计 | 392.674 | 15.43% | — | — | 409.070 |

两核在 EP 关时合计 **392.674 rank-ms，占 15.43%**；整个 mHC family 为 **15.76%**，两者不能混用。EP 开时两核合计 **409.070 rank-ms，占 14.51%**。4K/c8/EP 关下，两核合计约 **465.702 rank-ms，占 13.53%**。

这说明 mHC 是两种 EP 配置中都值得优化的常驻开销，但它不是本次 EP 性能下降的首要增量来源。

### 7.1 推荐实施方向

这两个核已经带有融合逻辑，下一步应围绕真实形状检查：

1. 小批量下的 tile、线程/任务划分是否合适。
2. 归约和归一化是否有多余访存或重复计算。
3. 中间结果是否反复写回，再由邻接操作重新读取。
4. 与前后算子的进一步融合是否能减少实际开销，同时保留需要的累加精度。

需要采集真实输入形状、dtype、stride、调用上下文，并在实际分布上做微基准，不能仅凭核名决定调参方案。

### 7.2 如何估计收益而不夸大

举例：若两个主核的累计时间减少 20%，按 4K/c1/EP 关的当前占比计算：

```text
累计 kernel 时间减少比例 ≈ 15.43% × 20% ≈ 3.09%
```

这只是该采样口径下的时间预算估算。是否降低 TPOT、降低多少，取决于关键路径、同步等待、执行重叠以及 profiler 关闭后的实际结果。

## 8. other 的拆解：碎片算子、候选 GDN 链与 attention 归类

### 8.1 4K 场景的 other 子类

下表按 kernel 名称进行操作级分类。数值的分母仍是 **该场景全部 kernel 时间**，不是 other 自身；两列各自合计分别约为 26.87% 和 25.66%。这是一种排查分类，不代表已确认模块归属。[S4]

| other 内部子类（按名称归类） | 4K / c1 / EP 关 | 4K / c8 / EP 关 |
| --- | --- | --- |
| 逐元素运算、激活、mask 与算术 | 9.19% | 8.47% |
| copy / cast | 4.67% | 4.13% |
| 名称明确的量化核 | 4.34% | 3.44% |
| 可能参与归一化的基础算子 | 2.26% | 1.89% |
| fill / range / zero | 1.14% | 1.10% |
| 索引 gather / scatter | 0.43% | 2.12% |
| 名称明确的 attention indexer / logits | 1.14% | 0.94% |
| 名称明确的 attention cache / index / metadata | 1.46% | 1.48% |
| 归属未定的 top-k 选择 | 1.20% | 0.92% |
| 名称明确的归一化核 | 0.26% | 0.25% |
| 其他 reduce / scan | 0.15% | 0.14% |
| 名称含 Mamba state 的前后处理 | 0.13% | 0.36% |
| 采样及辅助记录 | 0.07% | 0.06% |
| 其他未归属项 | 0.42% | 0.37% |

其中逐元素运算、copy/cast、量化和可能的归一化基础操作合计较大。后续更有价值的问题是“哪些操作属于同一段数据处理，能否减少中间结果和启动次数”，而非逐一追求每个微小核的局部加速。

### 8.2 一条值得验证的 GDN 相关候选链

数据中存在 10 个通用基础核，包括两类 copy/cast、MeanOps、sigmoid、pow、rsqrt、三类乘法和加法。4K/c1 中这些核各出现 5,440 次，4K/c8 中各出现 5,712 次，与 `fused_recurrent_gated_delta_rule_fwd_kernel` 的调用数对应。[S4]

候选核合计占比为：

| 场景 | 候选核累计时间（rank-ms） | 占全部 kernel 时间 |
| --- | --- | --- |
| 4K/c1/EP 关 | 191.459 | 7.52% |
| 4K/c8/EP 关 | 198.361 | 5.76% |

**相同调用次数只能支持关联假设，不能证明这些核都属于 GDN。** 应通过调用栈、顺序和中间张量确认它们是否构成同一条归一化/门控链，再考虑融合。

这组候选已经包含在 other 中，不能再叠加到总占比。若涉及归一化和门控，还要验证累加精度、极值输入及较长生成过程的数值稳定性。

### 8.3 attention 的现有分类不完整

部分名称明确的 MLA/MQA 相关核分布在其他 family，包括：

- `int8_paged_mqa_logits_kernel`
- `sparse_mla_index_remap_kernel`
- `vllm::concat_and_cache_mla_kernel<...>`
- `get_mla_metadata_kernel`
- `build_paged_mqa_schedule_metadata_kernel`

仅将这组最明确的候选补入，4K/c1/EP 关的 attention 相关占比就从 **6.39%** 变为约 **8.32%**，4K/c8/EP 关从 **8.59%** 变为约 **10.44%**。这仍未覆盖可能相关的投影、量化和通用准备操作。[S4]

所以，不能从原始 attention family 只有 6%～9%，就判断整个 attention 模块不值得优化。反过来，也不能把通用 `topk_2pass_row_kernel` 自动归入 MoE 或 attention。

### 8.4 长上下文索引核可作为后续补充

EP 关的 c1 场景中，`topk_2pass_row_kernel` 在 4K、16K、64K 的调用数相同，而加权单次时间约为 **17.414、24.491、38.457 μs**，呈现随输入长度标签上升的趋势。[S4]

另有 `OpaqueType<1>` 的 index / index_put 核，在 4K/c8 中出现少量约 2.21 ms 的长调用。它们可能影响特定阶段，但缺少时间线时无法确定是否处于首 token 或关键路径。建议在前述主要方向确认后，再单独检查实际索引规模、连续性和访存模式。

## 9. 低并发优先 GEMV，多并发提高 MoE GEMM 优先级

以 EP 关的 4K 场景对照：[S4]

| 子类 | 4K/c1 rank-ms | 4K/c1 占比 | 4K/c8 rank-ms | 4K/c8 占比 |
| --- | --- | --- | --- | --- |
| 名称含 GEMV 的核 | 418.750 | 16.45% | 20.939 | 0.61% |
| MoE GEMM | 204.475 | 8.03% | 500.931 | 14.55% |

### 9.1 面向低延迟：关注 GEMV

低并发 c1 下，名称含 GEMV 的核占比约 **16.30%～16.45%**。4K/c1 最大的一个 GEMV 核为：

```text
b16gemvt_kernel<256, 8, 4, 8, int, float,
               __maca_bfloat16, __maca_bfloat16>(...)
```

它累计约 **144.339 rank-ms，占 5.67%**，8 个 rank 合计 **5,440 次**，加权单次约 **26.533 μs**。核名模板参数不等于实际矩阵 M/N/K，需要从运行时补齐真实 shape。[S4]

优化重点可放在当前形状下的 kernel 选择、访存布局、重复读写及低批量执行开销。增大 batch 可能改变所选计算路径，但也可能影响排队与尾延迟，必须按业务时延目标权衡。

### 9.2 面向吞吐：关注 MoE GEMM 与专家负载

到 c4/c8，GEMV 的合计占比明显降低，MoE family 升高。4K/c8/EP 关中，MoE GEMM 占 **14.55%**，整个 MoE family 占 **19.91%**。[S2]、[S4]

这一阶段应重点核对每个专家实际收到的 token 数、GEMM 的真实形状、分组计算效率、排序/对齐开销，以及专家在 rank 间的分布。不要从出现了不同的 GEMM 模板名称直接推断性能退化，应先按功能和实际形状对齐。

`other GEMM` 与“GEMV 子集”、`MoE family` 与“MoE GEMM 子集”都存在包含关系，不能把父类和子类相加计算总占比。

## 10. rank 差异：整体较小，EP 下 MoE 的局部差异更值得查

10 个场景的 rank 累计 kernel 时间 CV 约为 **0.69%～1.46%**。同场景各 rank 的 kernel 调用数相同，没有显示整体调用量明显偏斜。[S3]、[S4]

EP 开的 5 个场景中，累计 kernel 时间最大值都出现在逻辑 rank 2，约高于本场景均值 **1.66%～2.28%**。这个重复现象值得对照物理映射，但不足以断言某张卡、链路或节点存在故障。

MoE family 的局部 rank 分布变化更明显：[S4]

| 场景 | 最小 rank 时间（ms） | 最大 rank 时间（ms） | 最大 / 最小 | rank 间 CV |
| --- | --- | --- | --- | --- |
| 4K / c8 / EP 关 | 85.625 | 85.802 | 1.002 | 0.06% |
| 4K / c8 / EP 开 | 83.458 | 92.715 | 1.111 | 3.39% |
| 16K / c4 / EP 关 | 79.877 | 80.046 | 1.002 | 0.06% |
| 16K / c4 / EP 开 | 78.256 | 88.624 | 1.132 | 4.13% |

这些差异提示应检查专家工作量、矩阵形状或等待关系，但不能仅靠耗时直接证明 token 路由失衡。相同调用次数也不代表相同工作量。

CV 在这里衡量同一次场景内 8 个 rank 的差异，不是多轮重复实验的不确定度。后续应把逻辑 rank、物理设备、专家集合、实际 token 数和通信到达时间放到同一张对照表中。

## 11. 高并发失败可能限制整体吞吐，需要单独定位

原始测试中，EP 关与开报告了相同的通过、失败和跳过集合。[S1]

| 输入标签 | 已通过并发 | 已测试但服务端失败的并发 | 后续跳过并发 |
| --- | --- | --- | --- |
| 4K | 1、2、4、8 | 16 | 32、64、128 |
| 16K | 1、2、4 | 8 | 16、32、64、128 |
| 64K | 1、2 | 4 | 8、16、32、64、128 |

这里的“最高已通过并发”不等于系统最大容量：例如 4K 的 9～15、16K 的 5～7、64K 的 3 没有测试。原表只有“服务端失败”，没有足够日志证明是 OOM、KV 容量不足或特定运行时错误。

4K/EP 关从 c1 到 c8 的输出吞吐从 **51.77** 增至 **314.48 token/s**，约 **6.07 倍**，仍在随并发增长。现有数据没有证明吞吐已经饱和。因此，修复或理解服务端失败，可能比继续优化小占比算子更影响可用吞吐，但具体收益目前未知。[S1]

建议先选 **64K/c2 通过 vs c4 失败**作为邻近对照，保存：

- 第一条服务端异常、worker 退出信息及请求错误码。
- 峰值设备内存、KV block 使用与调度准入信息。
- 实际输入/输出 token、并发状态及请求完成情况。
- 首次错误前后的时间线，避免仅分析失败后的连锁报错。

修复后在失效边界附近加密测试，再扩大并发范围。

## 12. 建议的最小验证实验与验收标准

### 12.1 第一轮：先让结论可复现

| 实验 | 固定项 | 变化项 | 必须回答的问题 |
| --- | --- | --- | --- |
| 采样覆盖核验 | EP 关、c1、同一部署版本 | 4K 与 64K；分别记录冷/热缓存 | 长 prefill 是否完整进入 trace？实际调度了多少未缓存 token？ |
| EP 对照复测 | 同输入集、同输出长度、同并发、同物理映射 | EP 关 / 开交替，先做 4K/c1 与 4K/c8 | TPOT 与吞吐退化是否稳定重复？ |
| 失败边界定位 | 同一服务配置与记录方式 | 64K/c2 与 c4 | 第一处失败是什么？资源与调度状态如何变化？ |
| 通信及准备链取证 | 先用一个可复现的 EP 对照场景 | 增加必要的时间线、shape 与通信信息 | AllReduce 增时来自传输、到达偏差，还是前序工作量差异？ |

性能复测与深度 profiling 分开运行：需要调用栈和 shape 时抓取短窗口；最终用户指标使用关闭 profiler 的运行结果，避免将采集开销纳入优化收益。

### 12.2 第二轮：一次验证一个实现改动

| 改动候选 | 局部验收 | 端到端验收 |
| --- | --- | --- |
| EP copy / index / fill 精简 | 对应核调用数/累计时间下降，读写和路由语义一致 | profiler 关闭后 TPOT 或吞吐改善，尾延迟与错误率不退化 |
| AllReduce 相关优化 | 通信大小、组、形状可比；关键等待或传输区间缩短 | 同负载 TPOT、E2E、吞吐改善 |
| mHC 小批量核优化 | 真实 shape 下两个主核累计时间下降，数值误差满足要求 | 目标并发范围内收益可重复 |
| 候选 GDN 链融合 | 确认归属后，启动次数和中间访存减少，数值一致 | 较长生成与目标负载下无精度或稳定性退化 |
| GEMV / MoE GEMM 调优 | 使用实际 M/N/K、dtype、stride 和专家 token 分布比较 | 在相应低延迟或吞吐目标下改进 |

共同要求：

1. 每次只修改一个可解释的因素，保留可回退基线。
2. 同时报告绝对时间、相对变化和有效请求数。
3. 在相同成功请求口径下比较，保留失败率和超时信息。
4. 检查输出正确性、数值误差、较长生成及专家路由一致性。
5. 以满足业务时延约束的吞吐和 TPOT 改善决定是否采用，不能只看某个 kernel 的排名下降。

### 12.3 后续架构对照：有条件地评估 TP4 × DP2

如果 4 张卡能容纳模型权重及目标负载所需 KV，且当前后端和设备拓扑支持，可在相同总计 8 张卡下，将 TP4 × DP2 作为后续实验候选。它可能改变单副本通信与总体并发能力，但本次数据尚未证明其优于 TP8。

若开展 DP 测试，应以服务端实际收到的请求 ID 和目标 rank 核实路由，确保逐请求路由头经过完整发送路径；旧数据集缓存可能影响客户端格式复用，仍需与服务端 prefix/KV cache 分开记录。

这属于后续验证方向，不能替代当前 EP 关基线的复测，也不代表 PP 或其他并行方式已在当前部署中得到支持。

## 13. 证据强度与暂不下结论的事项

| 类型 | 本文判断 |
| --- | --- |
| 已由给定数据确认 | 已测 9 组 EP 开的 TPOT 更高、吞吐更低；5 组 profile 中 collective 是累计时间增量的主项；指定 AllReduce 核调用数相同而单次时间增加；mHC、低并发 GEMV、other 是显著热点 |
| 有线索、需进一步验证 | EP 准备路径的冗余操作；专家负载导致的到达偏差；候选 GDN 基础链；逻辑 rank 2 对应的拓扑或负载差异 |
| 当前数据不能确定 | 完整冷 prefill 耗时；CPU 瓶颈占比；GPU/SM 利用率；互联带宽是否饱和；服务端失败根因；生产最大吞吐；TP4×DP2 的净收益；具体实现改动的端到端收益 |

如果开始实际优化，建议先把 **EP 准备链与 AllReduce 的因果关系**查清，再处理 **mHC 两个主核**；同时根据业务目标选择 **GEMV** 或 **MoE GEMM**。other 中的融合机会应在调用栈和数据依赖确认之后推进。
