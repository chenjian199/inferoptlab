# KDA 接入设计

查证日期：2026-11-20。本文描述 InferOptLab 的设计蓝图，尚未实现或验证这些接口。

## 1. 定位与公开能力边界

Kernel Design Agents（KDA）公开仓库提供由编程智能体执行研究、实现、验证和迭代的工作流。仓库将自身定位为仍在开发的研究原型，主要公开内容是流程、提示模板及技能引用；任务代码和评测材料放在独立工作区。[1]

因此，InferOptLab 按“工作流适配”接入 KDA，不假定存在稳定的 `kda.optimize()` SDK。`CodeOptimizationBackend`、`KDAWorkflowBackend`、`OptimizationTask` 和 `CandidateBundle` 都是本项目拟定义的接口或数据对象，不能写成 KDA 官方 API。

官方通用流程也考虑编译器、运行时和基础设施改动。[2] InferOptLab 的首个接入场景选择单个热点算子，后续可扩展代码优化范围；每次任务仍须限定修改范围和验收条件。

## 2. 输入契约：OptimizationTask

以下字段是建议的语义要求，正式字段名及序列化格式由本项目契约统一维护。

| 内容 | 必须表达的信息 |
| --- | --- |
| 身份与基线 | 任务 ID、契约版本、仓库 commit、基线补丁集合、构建环境及依赖指纹 |
| 目标与证据 | 需要改善的指标、端到端瓶颈证据、相关 trace 和基线测量引用 |
| 平台 | GPU 型号、工具链及其版本、已探测能力、可用 profiler |
| 修改范围 | 可编辑文件、允许的实现语言、禁止改变的接口和计算语义 |
| 开发用例 | 算子定义、真实形状、dtype、布局、输入分布、公开参考实现 |
| 开发验收 | 正确性条件、误差范围、开发测试和计时入口 |
| 资源预算 | 最大迭代次数、GPU 时间、Agent token、墙钟时间、输出空间 |
| 回接方式 | 推理框架中的调用位置、适用条件、不满足条件时的原实现回退路径 |

最终验收器的版本和规则由控制层锁定；Agent 可得到规则说明和开发用例，但不能得到隐藏验收数据的访问权限，也不能编辑正式验收器。隐藏用例仍遵守相同计算语义，区别在于未参与候选生成。

## 3. 适配器执行步骤

1. 控制层锁定基线及任务契约，准备独立工作区。
2. 适配器把任务转换为 KDA 风格的提示和本地资料入口，由 Agent 生成实现计划。
3. Agent 在限定文件范围内生成候选，执行开发正确性检查和微基准，按需申请性能分析。
4. 每个候选记录父候选、代码 hash、开发测量和失败原因；预算不足时终止当前迭代。
5. 适配器收集候选交给控制层，候选初始状态一律为 `unverified`。
6. 独立验证器在锁定的构建条件下重新构建，执行正确性、隐藏用例、微基准和端到端复测，再由验收模块决定接受、继续探索或拒绝。

步骤 2、3 可借鉴官方的任务约束、计划和迭代方法。[2][3] 资源调度、隔离、结构化输出及端到端验收属于 InferOptLab 要实现的能力。

## 4. 输出契约：CandidateBundle

候选包至少包含：

- 可复现的 patch 或 commit，以及基础 commit 和候选父链。
- 实现范围：平台、dtype、形状、布局、精度约束与回退条件。
- 构建说明、所需依赖、生成产物指纹。
- 开发正确性结果、微基准原始记录、profile 引用。
- `dev_claims`：Agent 对收益、瓶颈和限制的陈述，明确为待核验结论。
- `validation_status: unverified`，以及失败或未完成事项。

Agent 自报的加速比不得直接写入正式收益表。测量记录必须说明比较对象、样本、计时范围和重复次数；最终验收结果由独立记录关联候选包，不覆盖开发记录。

## 5. 资源与基线控制

GPU 通过执行层的租约分配，租约绑定设备集合、任务身份和过期时间。Agent 不能自行扩大设备范围。编译、采样、计时和 profiler 任务都计入预算；性能测量期间，执行层防止其他试验占用相同设备。

断点恢复只续接相同契约和基线。框架版本、工具链、目标 GPU 或基线发生变化时，生成新的试验身份并重新测基线。候选失败、超时和预算耗尽同样入账，避免只记录成功样本。

## 6. 跨平台和首个验收案例

KDA 官方 Wishlist 当前接受 NVIDIA B200、B300 社区任务。[1] 这不证明 BW1000 已有开箱即用的实现，也不意味着通用工作流必须绑定这两种 GPU。

InferOptLab 核心不强制依赖 CUDA 或 KDA。BW1000 接入需要独立核验编译器、运行时、代码生成、profiler 和正确性工具；能力缺失时返回明确的“不支持”或“待验证”，不伪装为成功。

首个案例应选择已在完整模型 trace 中确认的热点算子：提取真实工作负载，复现基线，生成一个候选，再接回原框架。完成标准是候选可复现、正确性通过，并在相同资源和负载下完成端到端比较；只获得微基准加速不算闭环完成。
