## 1. 首条纵向闭环

选择**一个实际可访问的平台、一个已能稳定推理的框架版本、一个固定模型和两类代表性负载**作为开发样板。两类负载应体现不同的真实使用条件，例如短输入与长输入；请求到达过程、输出规则、SLO 和资源预算由项目目标确定，不沿用示例值。

第一条闭环必须贯穿：冻结契约 → 基线测量 → 配置搜索 → 证据诊断 → 一个真实代码任务 → 独立验收 → 回接模型 → 组合复测 → 复现报告。

**v0.1 不能只有参数扫描。** 至少有一个代码任务完成导出、候选回传、构建、正确性验证、局部测量和端到端验收。候选可以由 KDA、其他 Agent 或工程师提供；平台需自动组织验证及记录。若候选生成仍由工程师触发，应明确标注，不能宣称已经完成自主代码生成。

候选最终可以被拒绝。完成闭环意味着能依据独立证据作出正确结论，不要求每个示范任务都制造正向性能收益。

## 2. 里程碑总览

| 里程碑 | 目标 | 主要产出 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| M0 | 契约、可比性、存储与租约 | 固定输入、版本化对象、可恢复的实验记录 | 不同口径不能混排，任务不重复占用资源 |
| M1 | 真实端到端测量 | 两类负载的基线、原始请求记录及环境证据 | 指标可追溯、运行可复现、无效测量可识别 |
| M2 | 配置搜索 | 受约束候选集、排名和淘汰原因 | 相同预算下比较完整部署，保留未覆盖范围 |
| M3 | 规则诊断与机制卡 | 假设、证据、区分实验和优化任务建议 | 至少一个问题能由实验支持或推翻 |
| M4 | 代码优化与独立验收 | OptimizationTask、CandidateBundle、AcceptanceReport | 一个真实代码候选完成局部与 E2E 验证 |
| M5 | 组合重调、复现包和第二平台 | 组合候选、最终报告、可迁移接口的验证证据 | 核心闭环可重放；新增平台按范围验证 |

M0—M4 加上 M5 的组合重调与复现包构成 v0.1 发布底线。M5 的第二平台是跨平台扩展门槛，可以在首条闭环之后完成；在此之前只声明已验证的单平台范围。

## 3. M0：冻结契约并建立实验底座

**输入**：首个模型/平台/框架组合，代表负载，性能与质量目标，资源和变更边界。

**实施内容**：统一 StudySpec、EnvironmentSnapshot、WorkloadSpec、DeploymentSpec、CandidateSpec、TrialSpec、RunRecord、MeasurementBundle、Hypothesis、OptimizationTask、CandidateBundle、AcceptanceReport。冻结单位、时间边界、SLO 与失败原因。实现 SQLite 单写者元数据仓储、制品引用、候选血缘和资源租约。

**产出**：一份可执行前校验的 Study、一组合法/非法契约样例、可恢复的模拟执行记录。

**完成标准（DoD）**：

- 未解析的 `REPLACE_*`、缺失单位、矛盾预算和不完整负载不能进入正式运行。
- 比较器拒绝未经允许的模型、环境、负载与评分差异，并报告具体字段。
- 控制端重启后保留 Run 历史；同一任务重投递不会无条件重复启动。
- 资源租约到期、Worker 失联与取消有明确处理，旧 Worker 不能持过期令牌继续登记有效结果。
- 模拟数据标为模拟来源，不进入真实性能排名。

## 4. M1：打通真实端到端测量

**输入**：通过 M0 的 Study、可用设备与模型、框架启动方式和已验证的基本环境。

**实施内容**：完成本地 Worker、首个设备及框架适配器、模型加载和就绪检查、负载发送、原始指标采集、预热与测量分段。执行与首个问题相关的最小硬件/算子校准，避免一次建设全部微基准。

**产出**：两类负载的真实基线、环境指纹、实际部署配置、请求级数据、失败记录和测量质量报告。

**完成标准（DoD）**：

- 同一 Trial 可独立复跑，并解释样本数、统计方法、波动及无效 Run。
- 冷启动、预热、编译和稳定测量不会混为同一延迟指标。
- p95 与请求级联合 SLO 分别计算；真实 ITL、chunk 间隔和 TPOT 不混用。
- 超时、崩溃、OOM 和取消后清理项目自身进程，保留证据并释放对应资源。
- 缺少必要观测时返回证据不足，不编造性能指标。

## 5. M2：配置搜索形成可比较候选

**输入**：真实基线、能力记录、有限搜索空间和实验预算。

**实施内容**：先实现能力剪枝和小规模条件枚举，再加入分层预算与提前停止。聚合部署和 PD 从同一候选层进入；每个候选表达完整角色、设备、并行组和运行参数。

**产出**：候选清单、Run 记录、有效候选排名、被拒绝/跳过候选及未探索范围。

**完成标准（DoD）**：

- 预算包含 P+D、draft model 和其他额外设备，卡数不由 TP/DP/EP 等数字机械相乘。
- PD 能力未验证或不支持时保留明确原因，继续其他有效分支；不静默换成聚合模式。
- 排名基于独立实测且满足硬性约束的指标，预测值和 Agent 自报值不混入。
- 固定负载对比与最大合格容量搜索分开报告；最终候选安排独立复测。
- 达到预算或停止条件后保存进度，结论限定为已测空间内的最佳合格候选。

## 6. M3：用证据产生可证伪的优化任务

**输入**：基线与候选差异、trace、校准结果和已知测量局限。

**实施内容**：先实现有限的确定性规则与证据引用，再按需加入 LLM 辅助解释。机制卡描述信号、替代解释、必需证据、实验、约束和回退；分类标签保持开放。

**产出**：Hypothesis、机制卡、区分实验，以及无法解释的问题清单。

**完成标准（DoD）**：

- 至少一个真实问题拥有原始证据、替代解释和可推翻假设的实验。
- 多流、多 rank 和通信重叠不通过简单耗时求和推导 E2E 影响。
- “预期性能”说明参考来源和适用范围；证据不足时不输出伪确定结论。
- 至少有一个机制能生成具体代码任务，避免诊断模块只会推荐参数。
- 未命中机制的问题仍保留，并可追加机制而无需修改封闭分类枚举。

## 7. M4：接入代码优化并独立验收

**输入**：经过诊断的 OptimizationTask、目标工具链、参考实现和固定验证协议。

**实施内容**：导出任务包，接入选定 Agent/人工后端，导入 CandidateBundle；构建与评测在独立环境执行。KDA 接入使用本项目适配协议，不假设外部存在稳定 SDK。

**产出**：至少一个真实代码候选、构建日志、独立正确性与局部性能证据、E2E AcceptanceReport。

**完成标准（DoD）**：

- 候选代码、参数、环境和制品哈希齐全，可定位其父候选。
- Agent 修改测试或自行报告通过不能推进独立验收阶段。
- 合法形状特化、误差容限、真实输入和回退路径按任务契约验证。
- 完成固定工作点的局部与端到端 A/B；支持通过、拒绝和证据不足三类结论。
- 框架能够重跑验证过程，而不是只接收一份外部性能表。

## 8. M5：组合重调、可复现交付与第二平台

**输入**：经过独立验证的配置/代码候选及其冲突关系。

**实施内容**：生成组合 CandidateSpec，重新验收并在同等预算下重调运行配置；输出包含失败候选的报告和复现包。随后选择第二个真实可用的平台/框架组合验证适配边界。

**产出**：最终推荐范围、固定点收益与重调收益、复现包，以及第二平台的资格报告。

**完成标准（DoD）**：

- 单项收益不相加；组合实际测量，冲突与回归可追溯。
- 另一工作目录或干净执行环境能依据复现包恢复指定候选并重跑规定测量；模型大文件可用版本和获取路径引用。
- 报告包含预算消耗、未覆盖空间、失败原因和最终采用依据。
- 第二平台复用领域对象与验收语义，不在核心模块增加厂商判断。
- 第二平台只对已实际通过的能力标记 `verified`；接口占位和 mock 不计入支持范围。

## 9. 两名工程师如何并行

工程师 A 主要负责契约、存储、编排、搜索、验收逻辑与报告；工程师 B 主要负责设备/框架适配、负载与采集、真实环境校准、profiling 和代码后端。两人共同评审指标定义、正确性规则和正式验收证据。

M0 的契约设计与首个平台准备可并行；M1 的执行器与测量适配并行；M2 的候选生成可与 M3 的 trace 采集并行；M4 的任务打包与独立验证器并行。每次并行都基于冻结的接口样例，避免用各自私有字段集成。

本计划不承诺精确人日。真实排期取决于平台可用性、模型是否已稳定运行、profiling 权限、测试耗时和外部 Agent 接入方式。先跑通样板闭环，再据实测成本估算扩大范围；Web 平台、多微服务和全厂商铺开均不作为首版前置。
