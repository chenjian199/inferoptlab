# 测量、诊断与实验设计

本文为 InferOptLab 的设计约定；不是任何模型/GPU 的已测结果。

第二步离线归因与第三步专项规划现已实现，入口见 [diagnosis](../diagnosis/README.md)、[analysis](../analysis/README.md)。已有 Qwen 实测可重放归因；具体方法和资料使用边界见 [阶段设计](diagnosis-analysis.md)。原生 profiler 采集及受控因果实验仍未实现。

环境与硬件校准的首版实现见 [tools/hardware](../tools/hardware/README.md)：固定计划、逐卡测试、原始样本和公式复算后导出配方。当前覆盖 MetaX inventory、GEMM 和设备内复制；下文涉及的主机传输、集体通信及其他层级仍按各自协议实施。

## 1. 四层测量体系

| 层级 | 要回答的问题 | 主要测量 |
|---|---|---|
| 环境与硬件校准 | 设备和互联是否按预期工作 | 显存可用量、主机/设备拷贝、形状相关 GEMM、通信延迟与带宽、拓扑 |
| 算子与局部模块 | 相同输入下实现是否低效 | 形状/dtype/布局、调用次数、设备时长、访存、同步、临时分配 |
| 模型执行 | Prefill/Decode 与状态如何推进 | 各阶段时间、有效 batch、KV/状态占用、rank 等待、调度与主机间隙 |
| 在线端到端 | 在真实负载和 SLO 下能提供多少服务 | TTFT、TPOT/真实 ITL、E2E、失败率、队列、吞吐、合格率与资源成本 |

硬件峰值是参考条件之一。诊断优先使用同平台、相同 dtype/shape/拓扑的实测校准、已知后端、历史匹配样本与简化性能模型。不能把“低于峰值某固定比例”当作普适异常规则。

SGLang 官方区分在线服务、单批服务、离线吞吐和直接 ModelRunner 测量，说明这些层级不应混为一类。[S3] vLLM 官方 benchmark 文档也要求关注指标语义与缓存状态。[S2]

## 2. 先固定测试协议

Study 的核心协议需包含：模型与 tokenizer revision、请求来源及采样、长度规则、输出与采样策略、到达模式、并发/QPS、prefix/session 复用、预热、缓存准备、测量窗口、超时、重复和终止规则。

到达模式分开保存：

- `closed_loop`：固定或扫描并发，上一请求结束后才能发新请求；适合并发容量探索。
- `open_loop`：按独立到达时间发请求；适合固定流量/SLO 与排队行为。
- `trace_replay`：保留真实依赖、会话、间隔与输入分布；不能为提分重排依赖。

开环负载器若触及自身并发上限或 CPU/网络瓶颈，实际发送过程可能改变；必须记录 planned/actual send time 和 client queue。不能把限流后较低的实际负载仍标成原目标 QPS。

## 3. 基线 B0、B1、B2

| 标签 | 定义 | 用途 |
|---|---|---|
| B0 | 目标环境中功能正确、可复现的初始部署 | 测迁移/整体工程起点 |
| B1 | 在固定预算内，现有实现经过配置搜索的最佳合格候选 | 评估新增代码优化的增量 |
| B2 | 代码/机制候选集成且重新搜索后的最佳合格候选 | 最终交付 |

标签关联真实 Candidate ID，不允许覆盖旧基线。搜索 B1 的预算也记录。先测 B1 与代码改动的固定点差异，再比较相同搜索预算下的 B1/B2；避免把原本可通过普通参数得到的收益全记给新 kernel。

若某个强制 case 的 B1 不满足 SLO 或 goodput 为零，不能计算该 case 的相对提升与几何平均。应报告绝对结果和“尚无可用相对基线”，按事先约定的可行性目标继续实验；不能补一个任意小分母制造巨大加速比。

## 4. v0.1 的必要测试矩阵

首条闭环至少选择短输入和长输入两个代表 case，每个 case 有低负载、容量附近与轻度过载观察点。若用户已有必须执行的测试表，以该表为正式验收集；探索点用于解释曲线，不替换验收集。

聚合与 P/D 各自从少量可行布局开始。在固定总卡数、实际拓扑、模型和相同 SLO 下比较。P/D 的就绪、KV 交接与质量能力未验证时，记录未覆盖原因并优先安排资格测试，而不是强行生成性能分数。

根据条件增加以下 profile：共享前缀与复用距离、长会话/状态增长、多模态编码、结构化输出、MoE 路由偏斜、投机接受率、冷启动/权重加载、通信拓扑、连续批处理干扰、动态扩缩容。触发条件来自模型与任务，不要求首版无差别跑全部组合。

## 5. 吞吐与 SLO 的项目定义

建议将客户端提交到首内容 token 的时间记为 TTFT；请求平均 TPOT 采用首 token 到末 token 的间隔除以 `n_out - 1`，要求 n_out > 1。真实 ITL 必须有对应 token 的时刻信息；SSE chunk 时间单列。

对固定请求集合，设第 i 个请求在完整生命周期中满足成功、TTFT 和预定 TPOT/ITL 等条件时 I_i=1，否则为 0。令 N 为冻结请求数，T 为从该集合首个提交到所有请求完成或达到固定超时的完整墙钟跨度：

`request_goodput = sum(I_i) / T`

`output_token_goodput = sum(I_i * actual_output_tokens_i) / T`

请求合格率为 `sum(I_i) / N`。计时分母包含该协议下的收尾和超时；不删除慢请求。这是适用于有限固定集合的验收口径，不与其他 steady-state 吞吐口径混比。

若采用固定稳态窗口计数，应单独冻结 warmup、窗口、跨边界请求、超时和 drain 规则；该协议给出独立指纹。窗口计数和固定集合结果不直接混合排名。质量任务和输出规则同时固定，不能通过提前终止输出提高分数。

同时要求 case 级 p95 与请求级联合合格率时，两者分别验收。每卡指标明确使用“分配卡数”还是“活动卡数”；同资源比较建议以前者为主，并另列活动资源效率。

## 6. 从测量到优化假设

`Hypothesis` 必须包含：观察到的偏差、具体比较基准、可能机制、替代解释、支持证据、证伪条件、最小区分实验和预计成本。

| 观察 | 可能解释 | 下一项区分实验 |
|---|---|---|
| TTFT 高但设备执行不长 | 排队、主机处理、请求组批、传输 | 对齐客户端/服务端/设备边界，固定低负载重测 |
| 通信时间看起来很高 | 大字节量、慢链路、rank 不平衡、无法重叠 | 测 message-size 曲线、rank 到达差、关键路径暴露时间 |
| 显存高且并发受限 | 状态容量、碎片、错误生命周期、临时物化 | 分解权重/KV/辅助状态/临时区，记录申请释放与峰值 |
| 相同 shape 的 GEMM 明显落后 | 后端、分块、布局、精度路径、边界退化 | 匹配 shape 微基准，检查真实后端和边界形状 |
| GPU 间隙多 | Python/CPU、同步、调度、编译/图覆盖不足 | trace 对齐 CPU launch 与设备空隙，受控移除一项因素 |
| kernel 都很快但整体慢 | 重复工作、队列、串行生成轮次、状态搬运 | 统计工作量与请求依赖，验证复用/调度/生成机制 |

以上只是起始假设集。观测缺口应输出“证据不足”并生成测量任务。不同流、不同 rank 的事件有重叠时，不能直接用事件时长求和推断 E2E 占比。

## 7. 优先级与实验预算

对已具证据的任务可用“可影响的关键路径比例 × 可改善空间 × workload 覆盖 × 证据可信度 / 实验和工程成本”作启发式排序。它是排序工具，不是保证收益的公式；缺失项用区间或未知标识，不能伪造精确分数。

v0.1 用规则剪枝、少量枚举、粗筛和最终复测即可。配置空间有依赖和离散模式，不能把非法组合当作低性能样本污染搜索器。OOM、unsupported 和正确性失败各自保留。

性能模型若存在，只产生 `predicted` 结果。缺少目标平台/模型覆盖时回到实测；不能把预测当作完成能力。AISim 作为可选预测器的事实边界见 [external-integrations.md](external-integrations.md)。

## 8. 防止测量和优化互相污染

正式计分关闭 profiler，另用相同代表负载做 trace；把 profiler overhead 和缺失事件记录下来。多节点使用时钟同步证据或因果事件关联，不能直接拼接不同机器 wall time 作精确关键路径。

最终候选用独立保留负载复测；重复运行顺序交错或随机化，并登记设备外部负载、频率、温度和 cache 状态。重复数/样本量随波动和尾部指标需要决定；模板的三轮只是起点，不是所有场景充分性的保证。

每次接受组合后重新识别瓶颈，重新分配剩余预算。达到预算、有效改善门槛、覆盖目标或无进一步可检验假设时停止，保存剩余问题。
