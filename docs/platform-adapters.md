# 平台适配器与能力协商

> 项目：InferOptLab · 契约版本：`schema_version: "0.1"`。本文规定未来实现的接口和行为。当前仓库为设计蓝图；出现的 NVIDIA、Ascend、MetaX、HYGON、SGLang、vLLM 或 KDA 名称均不表示已经实现或验证相应适配器。

## 1. 按能力组织适配，不按厂商名称推断功能

设备可被发现，只说明设备存在。框架能启动，只说明某个最小组合可运行。两者都不能证明目标模型、量化方式、并行组合、PD 传输或指定算子后端能够正确工作。

适配器应回答三个问题：当前环境是什么，候选需要什么，哪些需求已有验证证据。控制核心使用这些答案决定是否生成、执行或推荐候选；核心逻辑不散布 `if vendor == ...` 判断。

`EnvironmentSnapshot` 记录设备型号与标识、可用显存、拓扑、驱动和运行时、编译器、框架版本及 commit、容器标识、相关库与环境变量。无法采集的字段明确留空并记录原因，不填默认猜测值。

## 2. 适配器职责

| 类型 | 输入与输出 | 责任边界 |
| --- | --- | --- |
| 设备适配器 | 环境探测 → `EnvironmentSnapshot` 与资源遥测 | 设备、拓扑、内存、运行时和微基准入口，不负责选择最优部署 |
| 框架适配器 | `DeploymentSpec`、模型配置 → 启动计划及能力检查结果 | 参数映射、角色启动、就绪检查、实际后端核对和停止清理 |
| 测量适配器 | `WorkloadSpec`、`TrialSpec` → `MeasurementBundle` | 请求发送、时间戳、输出计数、统计与原始数据保留 |
| 分析工具适配器 | 运行目标与采集请求 → trace 及证据引用 | 采集和解释工具输出，不把工具特有指标强行映射为通用指标 |
| 执行环境适配器 | 运行计划 → `RunRecord` | 本地或远程执行、资源租约、日志、超时、进程树清理和恢复 |
| 优化执行器适配器 | `OptimizationTask` → `CandidateBundle` | 对接 KDA、其他 Agent、传统 autotuner 或人工候选，不决定最终验收 |

这些类型是内部协议划分，不要求各自成为独立服务。首版可以在同一个 Python 进程中实现控制逻辑，由 Worker 执行占用设备的任务。

## 3. 能力状态及证据范围

每个具体能力使用下列状态，并保存检查范围、证据和时间：

| 状态 | 含义 | 默认行为 |
| --- | --- | --- |
| `unverified` | 尚无足够证据判断目标组合 | 不作为已支持能力执行正式评分；允许安排受控能力探测 |
| `unsupported` | 有证据表明当前组合不支持或不满足必要前提 | 拒绝该候选，记录原因；条件变化后可重新探测 |
| `verified` | 指定环境、配置及输入范围内通过对应能力测试 | 允许进入后续实验，仍需通过候选自身的正确性和性能验收 |

验证范围必须足够具体。例如“设备 A 上框架 B 的某 commit，在指定模型和精度下完成聚合部署”不能提升为“该平台支持任意模型的 PD”。一个算子形状通过也不能提升为所有形状通过。

能力记录关联环境指纹及测试版本。驱动、框架、通信库、模型、编译选项或关键拓扑变化后，相关证据失效或降为 `unverified`；无关字段变化不应无条件清空全部历史证据。

## 4. Fail-closed 的准确含义

本项目约定：**不能证明候选满足必要前提时，不把它当作可用候选继续正式验收。**

这不意味着必须停止整个 Study。控制器可以跳过该分支、安排最小能力探测，或继续其他有效候选。探测失败还要区分基础设施错误与功能不支持，不能把一次网络或启动故障永久登记为 `unsupported`。

以下行为应明确禁止：

- 请求 INT8 实现失败后静默改为 BF16，再以原候选名报告。
- 请求指定通信后端却实际使用另一实现而不记录。
- 请求 PD 但启动聚合服务，继续参与 PD 对比。
- 缺少 token 时间戳时，用 SSE chunk 间隔替代真实 ITL。
- 没有 profiling 能力时，生成不存在的算子级证据。

允许的回退必须由任务契约授权、显式记录，并形成可识别的有效配置。实质改变被比较实现时生成新 `CandidateSpec`，不能覆盖原候选。

## 5. 候选检查顺序

每次执行前依次检查：

1. **结构有效性**：字段、单位、枚举、必填项和契约版本一致。
2. **静态兼容性**：模型与后端、数据类型、并行组合及编译目标相容。
3. **资源可行性**：设备集合、显存估算、进程映射和总预算满足要求。
4. **能力证据**：所需能力在当前环境和配置范围内已验证。
5. **最小运行探测**：加载、短请求、基本正确性和实际后端匹配。
6. **正式实验**：取得资源租约后运行 `TrialSpec`，产生 `RunRecord` 和 `MeasurementBundle`。

显存估算只是筛选依据；实际 OOM 仍需作为运行事实记录。静态检查、探测和正式实验的成本分别计入预算。

## 6. 部署与资源映射

`DeploymentSpec` 同时表达聚合和 PD 候选。对 PD，应列出 P/D 角色、实例数量、每个角色的并行组、设备放置、KV 格式、传输路径和交接要求。跨角色后端或精度组合必须有对应兼容性证据。

实际资源由角色、进程和物理设备映射确定。TP 与 EP 可能组织同一批设备，不能把 TP × DP × EP × PP 机械地当作卡数。预算检查以唯一设备集合为准，并核对 P+D 总计、draft model 的额外设备、辅助模型与共享显存占用。

框架适配器应在启动后回读或采集实际生效配置，记录解析后的默认参数与后端选择。控制器比较的是实际运行配置，而不是未经核实的启动请求。

## 7. KDA 等优化执行器如何接入

项目定义自己的适配协议，不依赖假设存在的官方 KDA RPC：

1. 将 `OptimizationTask` 导出到独立工作目录，包含语义、输入范围、参考实现、开发测试、基线和预算。
2. 启动选定工作流，记录模型与工具配置、任务版本和迭代日志。
3. 收集代码补丁、候选实现、适用范围及初步 benchmark，形成 `CandidateBundle`。
4. 外层验证器独立运行正确性、微基准与端到端验收，生成 `AcceptanceReport`。

不同平台可以采用不同代码生成语言、编译器和性能分析工具。任务契约、制品结构和验收语义应保持一致；尚未完成目标工具链适配时，状态保持 `unverified` 或依据证据标为 `unsupported`。

## 8. 首个适配器的完成标准

首版优先实现一个实际可访问的平台与一个框架，完成探测、启动、停止、测量、失败恢复和结果导出。其他目录可以保留接口占位，但必须清楚标明未实现。

适配器进入“可用于实验”的最低要求为：成功运行一个真实模型；完成至少一个确定正确性的请求；核对实际配置；输出可追溯的测量；在超时或失败后回收自己的进程与资源；留下环境和证据范围。PD、量化、特定算子后端等能力分别验证，不随基础启动能力自动通过。

每个适配器还应具备不依赖 GPU 的契约测试，以及真实环境下的集成测试清单。模拟结果只验证控制路径，必须标明 `mock` 来源，不进入真实性能排名或平台支持声明。
