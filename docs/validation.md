# 验证与验收设计

> 项目：InferOptLab · 契约版本：`schema_version: "0.1"`。本文是项目设计约定。当前交付为设计蓝图，尚未实现真实 GPU 测试、平台适配或性能验证；示例指标及规则不代表已经取得的测试结果。

## 1. 先定义什么算成功

`StudySpec` 在搜索开始前固定资源预算、质量要求、SLO、目标函数、允许变更范围及实验预算。`WorkloadSpec` 固定请求来源、输入分布、到达方式、输出规则、缓存状态和评分窗口。`TrialSpec` 说明本次测量的目的、候选、重复安排及验收规则版本。

一次验收至少回答四个问题：计算结果是否正确，实验是否可比较，SLO 是否满足，目标函数是否改善。不能用“算子更快”替代“整体更快”，也不能用“整体吞吐提高”抵消正确性或硬性 SLO 失败。

如果搜索过程中调整精度容限、请求分布或 SLO，必须生成新的任务契约版本并重新建立对应基线。已有结果保留原口径。

## 2. 固定资源预算与可比性

比较前核对 `EnvironmentSnapshot`、`DeploymentSpec` 和实际启动记录。设备预算按**实际占用的唯一设备集合**核算；P 与 D 的设备合计计入预算，独占的 draft model GPU、额外模型副本及其他加速器角色也必须计入。共享设备上的辅助模型还要记录显存和计算占用。

TP、DP、EP、PP 只描述并行组织，不能直接把这些数字全部相乘推算卡数。应核对进程到设备的映射、并行组成员以及角色是否重叠。例如，同一组设备可同时承担 TP 与 EP 的组织关系。

固定的比较条件还包括模型与权重版本、量化和精度条件、框架版本、拓扑、负载、缓存冷热、预热、计时边界及采样规则。必须区分：

- **固定负载比较**：在相同到达过程下比较延迟和有效吞吐。
- **容量搜索**：寻找各候选满足同一 SLO 的最大承载负载，最后重测候选边界。

不同框架或设备允许用于专项比较，但报告必须将变化项列为实验变量，不能视为单一代码补丁的收益。

## 3. SLO 与计时口径

### 百分位约束与请求级约束分别验收

`p95(TTFT) ≤ 阈值` 是一组请求的分布约束。请求级 SLO 则定义每个请求是否同时满足 TTFT、ITL、完成状态等条件。两个指标分别达到 p95，并不能证明同一批 95% 请求同时满足两个指标。

因此，`StudySpec` 应明确选择百分位约束、请求级合格率约束，或同时采用。`MeasurementBundle` 保留请求级记录和聚合统计；禁止只保存平均值，禁止通过各轮 p95 的简单平均替代合并样本或规定的跨轮统计。

### ITL 必须有 token 时间依据

TTFT 的默认客户端边界为“请求提交至收到首个有效输出 token”，包含该边界内的排队和传输。服务端计算时间可以另外记录，不能与客户端 TTFT 混用。

真实 ITL 需要相邻输出 token 的可观测时间戳。SSE 的一个事件可能包含多个 token，因此 SSE chunk 到达间隔必须标为 `chunk_interval`，不能直接称为 ITL。`(完成时间－首 token 时间)/(输出 token 数－1)` 是请求平均 TPOT 的一种定义，同样不能用于还原 ITL 的尾部分布。

当后端只能提供 chunk 时间时，token 级 ITL 标为不可测；若它是硬性验收条件，结果为“证据不足”。补齐时间戳能力或另立评分契约后才能继续对应验收。

### 吞吐的分母与计数边界固定

输出吞吐、总 token 吞吐和请求吞吐分别记录。有效吞吐只统计满足预先规定条件的请求或 token，并明确失败、超时、截断及跨测量窗口请求的处理规则。跨窗口归属策略必须一致，不能通过丢弃慢请求美化吞吐。请求合格率与有效吞吐应同时输出。

## 4. 正确性验证

`OptimizationTask` 固定数学语义、允许输入范围、参考实现、误差规则、布局与形状特化范围。形状特化可以合法采用，但必须验证该特化覆盖范围内的全部规定语义；未覆盖输入应正确回退或明确拒绝。

验证集至少区分公开开发用例、独立验收用例和真实模型提取的代表输入。需要覆盖正常形状、边界形状、不同数据分布、动态长度与状态生命周期。低精度、量化、采样或近似算法改变应按其任务约定增加模型质量检验；不能只看逐元素误差，也不能要求所有算法都逐位一致。

Agent 可提交 `CandidateBundle` 及初步结果。最终验证器、验收规则和独立验收数据由外层系统管理；候选不得通过修改评分器来取得通过状态。

## 5. 测量有效性与复测

资源租约防止候选共享同一测试设备而互相干扰。记录设备利用率、频率、温度、功耗状态和外部进程；出现超出任务容忍范围的干扰时，保留记录并标记该次运行无效。

编译、加载、预热、稳定测量和清理分别记录。profiler 运行用于诊断，不直接替代关闭 profiler 后的性能验收。编译及加载成本若属于目标场景，应单列验收，而不是隐去。

重复次数、持续时长和不确定性判据由 `TrialSpec` 给定。对最终候选安排独立复测，必要时交替运行基线与候选以识别环境漂移。大量候选中筛出的最高分仅是搜索结果，不能代替最终复测。收益小于预设最小改善幅度或波动范围时，结论为证据不足。

## 6. 从局部通过到整体验收

候选按以下顺序进入验收：

1. 核对环境、制品哈希、能力状态与实验契约。
2. 验证编译、加载、正确性和基础运行稳定性。
3. 对独立算子或局部模块测量性能，检查适用形状和回退路径。
4. 接回完整模型，复测相同负载下的 SLO、吞吐、显存和失败率。
5. 在代表性负载及最终保留用例上验证收益与回归。
6. 对多个有效变更的组合重新验收，并追踪各候选的父子关系。

GPU 事件、通信和多 rank 耗时可能重叠，不能直接求和解释墙钟时间。诊断报告应说明关键路径证据及不能归因的部分。各项优化收益不能相加作为组合收益。

## 7. 必须保留的证据

| 契约对象 | 最少证据 |
| --- | --- |
| `StudySpec` / `WorkloadSpec` / `TrialSpec` | 固定的目标、负载、评分与测量规则版本 |
| `EnvironmentSnapshot` / `DeploymentSpec` | 环境标识、设备集合、拓扑、角色与进程映射 |
| `CandidateSpec` / `CandidateBundle` | 父候选、完整有效配置、代码补丁及制品哈希 |
| `RunRecord` | 实际命令、起止时间、状态、退出原因、日志引用 |
| `MeasurementBundle` | 原始请求数据、统计方法、样本数、单位、有效性和 trace 引用 |
| `Hypothesis` | 瓶颈依据、反证、待补证据及可证伪实验 |
| `AcceptanceReport` | 各门槛结果、采用或拒绝原因、有效负载范围和复现入口 |

## 8. 结果语义

`AcceptanceReport` 使用“通过、拒绝、证据不足”三个设计状态，并逐项记录原因。失败运行还应区分 OOM、编译失败、超时、正确性失败、SLO 失败、基础设施故障和能力未验证，避免被汇总为相同的性能低分。

只有满足任务全部硬性条件且最终复测通过的候选，才能进入该任务的推荐集合。“证据不足”不能按成功处理，也不能推断其一定不支持。
