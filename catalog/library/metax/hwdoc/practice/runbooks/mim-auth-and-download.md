# MIM 登录与镜像下载排障

适用于本次 MIM registry 访问和大层下载排查，观察日期 2026-11-22。流程来自[部署案例](../cases/2026-11-22-glm53-w8a8-tp8/README.md)，不规定所有账号通用的登录用户名格式。

## 把登录与传输分开验证

1. 在服务器本地交互式完成 MIM 登录。手机注册的账号使用平台提供的 MIM API 密钥流程；登录身份格式以该账号的官方说明为准。不要将密钥放入命令参数、聊天、shell 历史或知识库。已有登录成功状态时先复用，不反复重置凭据。
2. 记录 registry 鉴权状态，再记录目标仓库 manifest 的状态和 digest，最后单独验证 blob 读取。匿名 token 签发成功不代表具有目标仓库的 pull 权限；401、仓库未授权和已授权后的超时是不同问题。
3. 对比直连与按进程代理。先检查当前进程是否继承失效代理；本例曾指向不可用的 `127.0.0.1:7890`，只在排查命令中清理相关环境变量。
4. 只输出状态码、耗时、传输量及校验结果。避免输出认证头、Docker credential 内容和带签名的重定向 URL。

本例已有服务器凭据的鉴权及 manifest 均返回 HTTP 200。之后仍发生 `connection timed out` 和 `unexpected EOF`，所以不能把下载故障归因于 MIM 密钥。证据：[摘要](../cases/2026-11-22-glm53-w8a8-tp8/evidence/deployment-summary.json) 的 `registry_diagnostics`，原记录位置及哈希见[资产清单](../cases/2026-11-22-glm53-w8a8-tp8/artifacts.json)。

## 判断是否支持断点续传

向同一不可变 blob 请求一个已知字节区间，只有返回 **206** 且 `Content-Range` 与请求和对象总长一致，才可把返回内容写到对应偏移；最终仍需验证整体 digest。响应 **200** 时不得直接追加，否则会损坏文件。把旧前缀重新下载并丢弃不是高效的 Range 续传。

本例被测大 blob 忽略 Range 返回 200，长连接多次中断；加代理后也未完成原镜像。保留已校验层、部分文件和失败事实，不将“有下载进度”写成“镜像拉取成功”。SDK 的分段下载路线要求严格区间校验和 SHA256，最终完成；不能由此推断 registry 的每个 blob 也支持续传。

## 下载失败后的可复用路线

有完整离线包可按厂商渠道申请；本例最终选择已缓存的不可变基础镜像，在新容器中安装已验证的官方 SDK 与 wheel。保留旧容器、宿主机驱动和 SDK，记录重建产物的新 image ID 和实际版本，不能沿用原 MIM 镜像的兼容性标签。

本例原 MIM 镜像不可用、独立基线可用；实际 SDK 为 3.9.0.29，与候选 MIM 中记录的 3.9.0.31 不同。完整依赖与构建入口见[独立环境指南](isolated-metax-environment.md)。后续重试应先确认现有层和下载任务，避免多进程重复拉取同一大文件。
